Cybernaut internship · Mini Project 1 · WEB-02 · Web scraping

ScholarTrack

A scholarship and fellowship deadline tracker. It reads approved official websites on a schedule, turns each announcement into clean data, notices when a deadline changes, and shows students a searchable dashboard that always links back to the official page.

31schemes
National Scholarship Portal, student applications close 31 Oct 2026, 23:59 IST. Read from the official page as Student Application Open till : 31-10-2026.
262real notices collected
4official sources
4page layouts handled
78automated test cases
~3,800lines of code incl. tests
Say it in one breath"Scholarship information is scattered and goes out of date. ScholarTrack collects it from official sources only, never guesses a deadline, tells you when a date changes, and always sends you to the official page to apply."

01 · WHYProblem and users

Scholarship notices are spread across government portals, university sites and funding bodies. Each uses its own layout and date format. Dates get revised and notices get withdrawn, while copies on blogs and aggregators go stale. Students miss deadlines or act on wrong information.

Project objectives (from the brief) and how they are met

ObjectiveWhat ScholarTrack does
Collect time-sensitive announcementsScheduled collection from 4 official sources (NSP, USIEF, CSC UK, EU Erasmus Mundus)
Normalise eligibility, benefits, deadlinesDeadlines become UTC instants with their timezone; study level, funding type and subject are normalised; eligibility keywords are highlighted
Warn when dates change; separate confirmed from unknownVersion-aware change history and one alert per meaningful change; unknown deadlines stay unknown and are labelled
Searchable, source-linked dashboardSearch, topic picker, filters, timeline, alerts; every card links to the official page

Personas

Aisha, final-year undergraduate

Wants master's funding, has little time, finds government portals confusing. She picks "Postgraduate" and "Fully funded", checks the timeline weekly, and opens the official page before applying.

Mr. Rao, scholarship office advisor

Advises hundreds of students and can't re-read every site. He relies on alerts to learn when a deadline moves or a notice is withdrawn, and forwards the official link.

Usefulness and limits of scheduled monitoring

Useful: one place, sorted by urgency, with change alerts and honest freshness labels. Limited: it is not real-time (each source is checked every 6 hours or daily), it only covers approved sources, and it can't decide eligibility.

05 · SCRAPINGCollection: fetcher and adapters

Polite fetcher (app/fetcher.py)

  • robots.txt first: 404 means no rules; 401/403 means disallow everything; 5xx means skip and flag. Crawl-delay is honoured.
  • Rate limit: at least 2 seconds between requests to the same host.
  • Timeout and retries: 20 s timeout, at most 3 attempts with exponential backoff (1 s, 2 s). Retries only on 429/5xx/timeouts, never on 403/404.
  • Safety: refuses redirects to other hosts, non-HTML content and responses over 2 MB. The User-Agent identifies the project.
  • Clear errors: each failure has a kind (network, timeout, http_error, robots_disallowed, parse_empty …) that is shown in the operator dashboard.

Four adapters, one per page layout (app/adapters.py)

AdapterPage shapeUsed byHow it reads it
tableHTML table, one row per noticeDemo portal AMaps columns by header text, not position, so reordered columns still work
cardsRepeated cards with a heading linkErasmus Mundus, demo BFollows "Next" pagination (up to 20 pages); unlinked items point to the catalogue page
blocksBlocks with "Label : value" badges, grouped by ministryNSPTakes the "Student Application Open till" badge, not the institute-verification dates; flags renewal-only schemes; uses the guidelines PDF as the official link
detail_pagesIndex page linking to one page per scholarshipCSC UK, USIEFFetches each page; reads the deadline with configured rules (a sentence pattern, or the table row labelled "Application deadline")

Selectors and labels live in sources.json, so a site redesign often needs only a config change. Malformed rows, missing fields and duplicates are skipped with a warning instead of crashing the run.

  • Year inference only happens when a weekday is given and exactly one year near today matches it. Otherwise the deadline stays unknown.
  • Study level: School, Diploma, Undergraduate, Postgraduate, Doctoral, Postdoctoral, Professional. Indian terms are handled: post-matric covers class 11 to PG; pre-matric means school.

07 · PERSISTENCEDatabase design

erDiagram
  sources ||--o{ notices : publishes
  sources ||--o{ scrape_runs : "checked by"
  notices ||--o{ changes : "has versions"
  changes ||--o| alerts : "raises once"
  alerts ||--o{ delivery_log : "delivered via"
TableKey columnsConstraints that matter
sourcessource_id, adapter, refresh_minutes, last_status, consecutive_failuresCHECK on adapter and status values
noticesnotice_id, source_id, url, provider, education_level, discipline, region, benefit_text, eligibility_excerpt, due_at, timezone, captured_at, verified_at, content_hash, notice_status, versionUNIQUE(source_id, external_key), FK to sources, CHECK on status
changeschange_id, notice_id, version, change_type, previous_deadline, updated_deadlineUNIQUE(notice_id, version)
alertsalert_id, change_id, message, delivery_statusUNIQUE(change_id), so one alert per change
delivery_log, scrape_runsEvery delivery attempt and every refresh runAudit trail for the operator
  • Primary key: notice_id = SHA-1 of source + the page's own key (or URL). The same notice always gets the same id, so a correction becomes an update, never a new notice.
  • Idempotent upsert: each refresh runs in one BEGIN IMMEDIATE transaction. Running it twice on the same page changes nothing (tested).
  • Migrations: 001_init.sql and 002_real_sources.sql (rebuilds sources using the standard SQLite procedure, keeps all data). Applied automatically at start-up.
  • Secrets: the operator token comes from an environment variable or a git-ignored file, never from source code.

08 · REAL-TIME UPDATESChange detection and alerts

  1. A content hash is computed from the fields a student cares about (title, provider, level, subject, benefit, eligibility, deadline instant, status). Re-formatting the same date doesn't change the hash.
  2. Same hash: only verified_at is updated.
  3. Different hash: the notice is updated, version goes up, and a changes row records old and new deadlines. The type is one of deadline_revised, deadline_set, deadline_removed, withdrawn, reinstated, details_updated.
  4. Every type except details_updated raises exactly one alert. Alerts are delivered to a log (safe demo mode) or an optional webhook, and every attempt is written to delivery_log.
  5. A notice missing from a complete, successful read becomes unlisted. It is not deleted and not called "withdrawn". If the read was incomplete, nothing is marked.
A real example from todayAt 09:12 UTC the Commonwealth Master's and PhD pages said "The closing date for applications is 16:00 BST on Tuesday 20 October". By 11:50 UTC that sentence had gone, because applications had closed. ScholarTrack recorded two deadline_removed changes and raised one alert each: "Deadline removed for 'Commonwealth Master's Scholarships' (was 20 Oct 2026, 16:00 Europe/London); treat it as unknown". I confirmed against the live page that the sentence really was removed.

10 · UI & USABILITYThe dashboard

1. Find notices

A big search box: tap it (or Topics) to pick ready-made topics such as "Engineering & technical (57)" or "For girls & women (2)". Each topic is checked to have results. Study level and funding type dropdowns list only values that exist, with open counts. Quick picks and More filters (programme, dates, sort) round it out.

No dead ends

If nothing matches every filter, the closest matches are shown with a plain note, e.g. "To find them we removed the deadline date filter." In a test of all 189 level × type × quick-pick combinations, none was empty.

Notice cards

A days-left badge (red under 7 days, amber under 30), the deadline in the source's timezone and in yours, "assumed" flags, a verification pill, the official link, and a change history.

2. Timeline · 3. Alerts · Help

Deadlines grouped by urgency with text countdowns (never colour alone). Alerts with source citation and verification state. Help covers personas, data sources and limitations.

Operator tab

Token-protected. Shows source health, consecutive failures, run history (HTTP status, tries, found/new/changed), the alert delivery log, Refresh now, and the demo walkthrough controls.

Accessibility

Keyboard tabs, labelled controls, ARIA live regions, visible focus, light and dark themes, phone layout. Two browser windows stay in sync within 15 seconds.

14 · RESPONSIBILITYEthics, compliance and limitations

What we do

  • Only public pages; robots.txt respected; polite rate limits.
  • No login, no CAPTCHA bypass, no personal data stored.
  • Data minimisation: facts + links; no copied paragraphs from restricted sites.
  • Every notice credits and links to its source.
  • Honest freshness: stale data is never called live.
  • No automated eligibility decisions.

Known limitations

  • Not real-time: checked every 6 h (Erasmus daily).
  • Erasmus programmes publish deadlines on their own sites, so these show "not published".
  • Many USIEF and CSC deadlines have already closed for this cycle.
  • A few NSP schemes don't state a study level.
  • Subject is inferred from titles; timezone abbreviations like IST/CST are ambiguous.
  • Mentor and NSP permission still to be obtained.

18 · BE READYViva preparation

The brief says you must explain and change a parser or SQL query without generated code. Practise these two pieces until you can explain them in your own words.

Piece 1: how a deadline is parsed (normalize.parse_deadline)

  1. If the text is empty or says TBA / Rolling / Not announced → unknown.
  2. Find a date: ISO 2026-10-31, then 31 Oct 2026, Oct 31, 2026, then 31-10-2026. Only if none matches, try "weekday + day month" with the year rule.
  3. Remove the date from the text and look for a time (16:00, 11:59 PM); none → 23:59, flagged.
  4. Look for a timezone after the time: an ISO offset, an IANA name, UTC+01:00, or an abbreviation like IST. None → the source's default zone, flagged.
  5. Build the local datetime and convert it to UTC for storage.

Practice change: add "HKT": "Asia/Hong_Kong" to TZ_ABBR and write a test for it.

Piece 2: the upsert (pipeline.upsert_notice)

SELECT * FROM notices WHERE notice_id = ?          -- seen before?
-- no  -> INSERT (captured_at = first_seen_at = verified_at = now)
-- yes, same content_hash -> UPDATE notices SET verified_at = ? ...
-- yes, new hash -> UPDATE ... version = version + 1

Practice query: "list notices closing in the next 7 days, soonest first":

SELECT title, due_at FROM notices
WHERE notice_status = 'active'
  AND due_at > strftime('%Y-%m-%dT%H:%M:%SZ','now')
  AND due_at <= strftime('%Y-%m-%dT%H:%M:%SZ','now','+7 days')
ORDER BY due_at;

Likely questions

Why store deadlines in UTC?

So every comparison and filter is between instants. 31 Oct 23:59 IST and 31 Oct 18:29 UTC are the same moment. The original zone is stored too, for display.

How do you avoid duplicate notices and duplicate alerts?

The notice id is a hash of source + page key, so the same notice always maps to one row. UNIQUE(notice_id, version) on changes and UNIQUE(change_id) on alerts make a second identical run unable to create another alert.

What happens if a website changes its design?

The adapter finds nothing. The run fails as parse_empty, the source shows "needs review", and existing notices stay visible but labelled. Usually only the selectors in sources.json need updating.

Isn't scraping illegal?

We only read public pages, follow robots.txt and rate limits, store facts rather than copied text, credit and link every source, and documented each site's terms. Where a site asks for permission to reproduce (NSP), that is flagged for the mentor and the site.

Why are many deadlines 10 days away?

All 31 NSP central schemes share one closing date, 31 Oct 2026. The list is sorted by soonest deadline, so they appear first.

Why do Erasmus programmes have no deadline?

The EU catalogue doesn't publish one; each programme sets its own. We show "not published" instead of guessing.

How is "real-time" achieved?

Scheduled monitoring per source (6 h / 24 h), fast retries after failures, and live browser updates: the page polls a data-version number and reloads when it changes.

What would you add next?

See Future work: email alerts, per-student watchlists, more sources, reading Erasmus deadlines from programme sites.
